1背景与目标

1.1 背景

租房中介公司目前依赖人工在小红书上找线索:搜索"成都租房"等相关笔记,在求租帖下评论自家房源吸引私聊,或私信评论区的潜在客户,引导对方添加微信成为线索。该过程人力重、效率低、难规模化。

1.2 目标

做一套工具,自动完成"检索相关笔记 → 按条件匹配 → 自动评论/私信(带匹配房源图文) → 引导加微/留联系方式 → 线索沉淀"的全链路获客动作,在可控封号风险下放大中介的获客产能。

1.3 一句话定义

一个"每账号一个桌面客户端 + 一个中央汇总后台"的小红书全自动获客系统,客户端驱动用户真实浏览器在小红书上自动获客,后台统一观测所有账号与线索。

2角色与用户

角色使用什么职责 / 诉求
中介运营(客户端使用者)桌面客户端(1 人/1 账号)配置匹配条件、维护房源素材、启动自动化、接手高意向对话、查看本账号线索
管理者(后台使用者)中央后台跨账号观测运行情况/配额/健康、汇总查看与管理全部线索
租户(Tenant)—(数据隔离单位)一个公司/团队 = 一个租户,其下多个账号与客户端;P2 租户管理 UI 后期做,本期 schema 预留

3核心业务流程

1 检索

找笔记

按城市/关键词检索求租&房源笔记及其评论区

2 匹配

分层漏斗

地区+时间→意向→预算户型→诉求语义,打分命中

3 生成

话术+配图

AI 按诉求生成话术,从房源库选匹配房源与图

4 触达

评论/私信

全自动直发(限频+反检测),四类动作

5 转化

引导加微

诱导对方给微信,识别入库;高意向转人工

6 沉淀

线索归集

本地保留+上报后台,预留外部对接

两条玩法(都要支持) ① 在求租帖下评论自家房源,吸引对方私聊;② 对房源帖/评论区提问者主动私信引导。匹配引擎根据"意向类型"判断笔记走哪条玩法。

4功能需求

4.1 检索 P0

  • FR-1.1 按城市 + 关键词检索相关笔记(求租 / 房源)。
  • FR-1.2 读取笔记正文、标签、发布时间、作者信息。
  • FR-1.3 读取笔记评论区,识别"问房子信息"的潜在客户评论。
  • FR-1.4 低频、模拟人工节奏地翻页/采集,受全局限频约束(见第 5 节)。

4.2 匹配引擎(分层漏斗) P0

层维度说明
L1 硬过滤地区 + 时间地区匹配可开关,且目标城市由用户自定义(可多城)——不绑定账号属地(人在 A 城、业务在 B 城的情况)。可细到区/商圈。时间 = 发帖/评论在配置的时间窗内。不满足直接淘汰。
L2 意向求租 / 出租识别笔记意向类型,决定走"评论"还是"私信"玩法。
L3 结构化预算 / 户型价格区间、几居室、整租/合租等结构化条件。
L4 语义诉求关键词LLM 提取"近地铁/带阳台/可短租/可养宠/押一付一"等软诉求,输出匹配分,并驱动选哪套房源、配哪张图。

FR-2.x 匹配条件可由运营在客户端配置;L1/L2/L3 为低成本规则筛,L4 为 LLM 精筛(失败时 fail-open 保留并标记待人工)。

4.3 内容生成(话术 + 房源配图) P0

  • FR-3.1 LLM 按笔记上下文生成个性化、不雷同的评论/私信话术(规避复制粘贴刷屏特征)。
  • FR-3.2 按 L4 诉求关键词从房源素材库匹配房源,附带对应图文("提到地铁→发地铁房")。
  • FR-3.3 话术中不出现明文联系方式(走第 4.5 节策略)。

4.4 触达动作(全自动直发) P0

四类动作全部要做,实现按风险从低到高排期:

动作说明风险建议排期
FR-4.1 自动评论笔记在匹配的求租/房源笔记下发带房源图文的评论中先做
FR-4.2 回复他人评论区在别人笔记评论区回复问房子的提问者中先做
FR-4.3 自动回复私信别人私信我→机器多轮自动应答中其次
FR-4.4 主动发起私信主动私信发帖人/评论提问者最高最后,最克制

4.5 加微转化 P0

主策略:混合(诱导为主 + 高意向转人工)。

  • FR-5.1 话术用暗语诱导对方主动留/加微信(不主动发我方联系方式)。
  • FR-5.2 微信号识别入库器:自动识别对方消息里的微信号/手机号/暗号并提取入库。
  • FR-5.3 对话意向分级器:LLM 判断对话意向/复杂度,达到阈值则标记转人工接手,客户端提醒运营。默认转人工触发:对方明确问价 / 约看房 / 索要或给出联系方式 / 连续多轮深入咨询(规则可配置)。
  • FR-5.4 话术库管理功能:提供让用户自行填写/维护诱导话术、模板与暗语的功能(用户用自己"在用且没被封"的真实话术),不内置写死。

4.6 房源素材库 P0 外部同步 P2

  • FR-6.1 工具内结构化录入房源:城市/商圈、价格、户型、整租合租、卖点标签、多张图。
  • FR-6.2 标签体系与 L4 诉求关键词建立映射(用于自动选房配图)。
  • FR-6.3 预留"外部同步接口",将来对接公司现有房源系统(本期不实现)。

4.7 线索管理 P0

  • FR-7.1 线索(对方微信/手机、来源笔记、对话、意向、状态)在客户端本地保留。
  • FR-7.2 线索与账号状态上报中央后台汇总(失败重试、断网不丢)。
  • FR-7.3 预留外部对接出口(企微/CRM/Excel 导出),本期不实现。

4.8 中央后台 P1(薄层)

  • FR-8.1 接收所有客户端上报的线索与账号状态。
  • FR-8.2 跨账号看板:每个账号的运行情况、配额用量、健康/限流状态可见。
  • FR-8.3 汇总查看与管理全部线索。
  • FR-8.4 数据按 tenant_id 隔离;P2 租户管理 UI 后期。
  • FR-8.5 后台为"观察者",不向客户端下指令(客户端自主运行)。

4.9 可配置性需求(横切) P0

原则:能配置的都不写死 系统运行参数必须由用户在客户端自助配置。本节只声明"哪些必须可配置"(需求层);具体的配置项明细、界面、字段、默认值、交互由后续《产品功能文档》定义,本文档不展开。
  • FR-C.1 检索配置:自定义目标城市(可多城、不绑账号属地)、搜索关键词、笔记类型(求租/房源)、时间窗(无预设默认,用户首次配置时填)、采集范围/翻页深度。
  • FR-C.2 匹配规则配置:四层各自的条件、阈值与启用开关(如地区匹配可整体开/关)。
  • FR-C.3 话术与配图配置:话术风格/模板/变量、是否带图及配图规则。
  • FR-C.4 加微策略配置:诱导话术/暗语(话术库见 FR-5.4)、"转人工"触发条件。
  • FR-C.5 限频与节奏配置:各类动作每日上限、操作间隔、工作时间窗、养号阶梯、紧急刹车——具体数值均可由用户配置(默认保守,小号实测校准)。
  • FR-C.6 房源库配置:字段定义、标签体系、标签↔诉求映射。
  • FR-C.7 系统配置:账号信息、后台上报地址、LLM 提供商/Key。

5防封号与养号(重点) P0

这是全自动方案能否存活的命根子 既然选了"全自动直发",必须把下列保护机制作为一等公民,与业务功能同等优先。
  • FR-9.1 反检测:CDP 驱动真实浏览器(isTrusted=true 输入)、贝塞尔鼠标轨迹、不均匀打字、阅读滚动节奏(复用 BOSS)。
  • FR-9.2 限频:每类动作(评论/私信/采集)独立的每日上限与操作间随机延时;支持配额浮动(±随机)破坏规律性。
  • FR-9.3 工作时间窗:仅在配置的工作时段运行,可按周几区分。
  • FR-9.4 养号阶梯:新号/低权重号自动降速,逐步放量。
  • FR-9.5 账号健康监控:检测限流/异常信号(如发送失败率、功能受限),异常自动降速或暂停并上报后台。
  • FR-9.6 紧急刹车(kill switch):一键/自动停止该账号所有自动化动作。
  • FR-9.7 不碰明文红线:不在内容/评论中出现明文微信/电话/二维码/外链(系统秒判违规)。

6账号 · 租户 · 后台模型

  • 一个客户端实例 = 一个小红书账号。
  • 一个账号绑定一个真实 Chrome / 一台机器(天然住宅 IP + 真实指纹,利于防关联)。
  • 一个租户下可有多个账号/客户端;后台按租户隔离数据。
  • 本期先跑通单账号;架构与数据模型按多账号/多租户预留,不返工。
  • 每个账号的运行情况在后台可见。

7非功能需求

类别要求
合规与风险承认违反平台协议与封号风险存在;以"克制 + 拟人 + 限频"降低风险;明确不做明文导流;附使用免责说明。
可靠性客户端断网仍可运行、本地不丢数据;上报失败可重试;任务崩溃可恢复(状态追踪表 + 心跳)。
安全本地敏感配置(如 LLM Key)加密存储;客户端与后台通信鉴权;线索数据按租户隔离。
性能动作吞吐以"安全"为先,受限频上限约束(非追求高 QPS)。
可维护小红书改版后页面选择器需可快速更新(刚性维护成本);页面操作层与业务层解耦。
可观测运行事件、动作流水、异常、配额可在客户端与后台查看。

9范围

MVP(本期)

  • 桌面客户端:单账号跑通"检索 → 四级匹配 → 话术+配图 → 四类触达 → 加微/转人工 → 线索本地入库"。
  • 工具内结构化房源素材库 + 标签映射。
  • 防封号/养号全套保护机制。
  • 薄后台:接收上报、跨账号看板、线索汇总查看;数据库带 tenant_id。

后期(P2)

  • 租户管理 UI;多账号矩阵的高级调度。
  • 房源系统外部对接同步;线索推送企微/CRM/Excel 导出。
  • 授权激活/收费产品化(如对外交付)。

明确不做

  • 不做逆向 API 直连(签名维护无底洞 + 高封号)。
  • 不在内容里发明文联系方式/外链。
  • 后台不远程操控客户端账号行为(本期)。

10关键风险与红线

  • 封号 小红书风控("天枢",200+ 维度)严打机器操作与站外引流;主动私信陌生人风险最高。
  • 合规 2025 起官方私信通为唯一合规导流通道,绕过它属违规;批量数据采集涉《个人信息保护法》。
  • 维护 小红书改版会导致页面选择器失效,需持续维护。
  • 连坐 多账号矩阵存在关联封禁风险,需防关联(IP/指纹/设备隔离)。
缓解 真实浏览器 + 拟人节奏 + 严格限频 + 工作时间窗 + 账号健康监控 + 紧急刹车 + 测试小号优先(主力号不裸跑)。

11成功标准

  • 单测试账号连续运行 N 天(待定) 不被封/限流。
  • 匹配准确率(命中真实目标客户)达到 目标值(待定)。
  • 每账号每日产出有效线索 X 条(待定)。
  • 加微/留资转化率较人工提升 目标值(待定)。
  • 后台可准确反映每个账号的运行与线索情况。

具体指标值待运营基线设定:需结合你们现有人工获客基线,或在测试小号试跑出数据后再定。

#问题决策结论
Q1"同城"如何判定?地区匹配可开关;目标城市由用户自定义(可多城、不绑账号属地);来源优先用笔记/主页城市 + IP 属地,细到商圈用 LLM 从文本提取。(见 4.2 / FR-C.1)
Q2时间窗 N 与基准?不设预设默认,做成可配置由用户首次填;基准:求租帖按发帖时间、评论区客户按评论时间。

Q4"转人工"判定标准?默认:问价 / 约看房 / 索要或给联系方式 / 连续多轮深入;规则可配置。(见 FR-5.3)
Q5房源结构化字段清单?下沉 明细 → 《产品功能文档》;需求层已由 FR-6.1 / FR-C.6 覆盖。
Q6LLM 用哪家?国产大模型(火山 Ark / 阿里百炼),具体型号待定;做成可切换 provider。
Q7后台部署 + 鉴权?云服务器 + Token 鉴权。
Q8本期是否做 license?不做(仅内部用);对外交付再加。
Q9成功指标目标值?下沉 待运营基线设定(现有人工基线或试跑数据后定)。
Q10加微话术样本?做成话术库管理功能由用户自填(见 FR-5.4);下沉 样本由用户提供。
