1为什么第一期先做"评论闭环"

理由说明
风险最低、需求已排期需求 4.4 把四类触达按风险排期:自动评论笔记(FR-4.1)、回他人评论区(FR-4.2)= 中风险"先做";主动私信(FR-4.4)= 最高风险"最后做"。第一期只取"先做"的两个。
能独立产生价值在求租帖下评论自家房源、在评论区回"问房子"的人——本就是中介现在人工在做的核心动作,自动化后立即有产出。
把地基串一遍接管浏览器→检索→匹配→内容生成→发评论→防封→落库,整条链全走通。第二期加私信/加微只是在这条链上接楼层,不返工。
不碰最高危动作不做"主动私信陌生人"(风控最狠),第一期存活概率最高,适合拿测试小号先跑。

3端到端流程(本期 5 步)

① 检索

找笔记

关键词×城市搜求租/房源笔记 + 评论区,去重入队

② 匹配

分层筛

L1 地区+时间硬过滤 → L2 意向(决定评论方向) → L4 诉求(轻)

③ 生成

话术+配图

LLM 个性化评论 + 按诉求选房配图 + 合规过滤

④ 评论

自动触达

笔记下评论 + 回评论区问房者(限频/拟人/可刹车)

⑤ 记录

沉淀监控

评论结果 + 潜客标记入库,实时流水可见

全程受"防封号"约束 每一步都在限频、工作时间窗、随机节奏、账号健康监控、紧急刹车的保护下运行——这是全自动方案能否存活的命根子(需求 5 章)。

5第一期验收标准(跑通的标志)

端到端 配置好策略与素材 → 控制台一键启动 → 系统在限频与拟人节奏下自动检索到匹配笔记 → 生成合规评论+配图 → 发出 → 记录可见 → 账号不被封。
#逐条验收
1能接管已登录的 Chrome 并确认账号在线(不需重新登录)。
2检索能按"关键词×城市"拿到候选笔记 + 评论区,去重入队。
3匹配能淘汰不符地区/时间的笔记,能区分求租/房源走不同评论方向。
4每条评论由 LLM 个性化生成、不雷同,附按诉求匹配的房源图,且不含明文微信/电话/二维码/外链(合规器拦截)。
5评论在每日上限 + 随机节奏下发出;紧急刹车能即时停止所有动作。
6评论结果(成功/失败/被删)与评论区"问房者"潜客被记录入库。
7出现限流/异常信号能自动降速或暂停并在界面提示(不静默失败)。

量化指标(连续运行 N 天不封、每日评论 X 条、命中率)待测试小号试跑后按运营基线设定(需求 11 章 / Q9)。

6不做项与后续衔接

第一期明确不做

私信(主动/自动回)、多轮自动沟通、加微识别入库、意向分级转人工、中央后台、外部对接、多账号/租户管理 UI、license。

第二期

在评论闭环上接「主动/自动私信 + 多轮自动沟通 + 加微识别入库 + 意向分级转人工 + 完整线索管理」。

第三期

中央后台(账号看板/线索汇总)+ 多账号矩阵 + 防关联调度。

不返工保证 数据模型从第一期起即带 tenant_id 与状态机预留;页面操作层与业务层解耦,小红书改版只需更新选择器(需求 7 章可维护性)。
